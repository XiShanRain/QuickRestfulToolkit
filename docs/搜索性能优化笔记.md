# 搜索框卡顿优化笔记（初学者向）

> 本篇记录 RestfulRadar 中「按 `Ctrl+Alt+/` 打开搜索对话框后，输入关键字时列表卡顿」这个问题的**成因分析**与**优化手段**。
> 面向刚接触 Swing / IntelliJ 插件开发的同学，尽量把每个技术点讲透。

---

## 一、先理解：界面为什么会“卡”？

### 1.1 什么是 EDT（事件分发线程）

Swing 界面所有操作都跑在一条特殊的线程上，叫 **EDT（Event Dispatch Thread，事件分发线程）**。
你按下键盘、鼠标点击、输入框内容变化、列表重绘……全部由这一条线程串行处理。

一条铁律：**EDT 上绝对不能做耗时操作**。
只要某个任务在 EDT 上占用了太久（比如几十毫秒以上），界面就会：

- 对键盘/鼠标没有反应（“卡住”）
- 画面不刷新（“白屏/闪烁”）

我们这次的卡顿，就是**每次敲一个字符，都在 EDT 上干了一堆重活**。

### 1.2 优化前的执行链路

```
用户敲一个字符
  └─ DocumentListener 立即触发 updateList()      ← 每个字符都触发！
       ├─ filterItems()：遍历全部结果（可能上千条）
       │     └─ 每条都调用 UrlPatternUtils.matches(...)
       │           ├─ 对 endpoint 路径做正则归一化 normalizeUserInput  ← 重复计算
       │           ├─ 编译正则 toRegex(...)                            ← 昂贵且重复
       │           └─ 构建候选后缀列表 buildCandidatePaths(...)         ← 重复
       │     └─ 再 sortedBy 整体排序                                    ← 每次全排序
       └─ listModel.replaceAll(filtered)：替换整个列表
             └─ JBList 重绘所有行，每行用 <html> 渲染富文本              ← 非常慢
```

一句话总结痛点：**没有防抖 + 大量重复计算 + 整表重绘**。

---

## 二、三个优化技术点

### 技术点 1：防抖（Debounce）

**概念**：用户连续操作时，不在每次操作都执行任务，而是“等用户停下来再做”。

类比：电梯门——有人陆续进来时，门不会每进一个人就立刻关闭启动，而是等一会儿没人按了再走。

**实现**（`RestSearchDialog.kt`）：用一个 `javax.swing.Timer`，输入变化时只重置倒计时，倒计时到点才真正过滤。

```kotlin
// 停手 120ms 后才过滤；isRepeats=false 表示只触发一次
private val filterTimer = Timer(FILTER_DEBOUNCE_MS) { applyFilter(textField.text) }.apply {
    isRepeats = false
}

// 每次按键：把计时器“重启”，重新计时
private fun scheduleFilter() {
    filterTimer.stop()
    filterTimer.restart()
}
```

**为什么用 `javax.swing.Timer`？** 因为它的回调**默认就在 EDT 上执行**，改界面（`listModel.replaceAll`）安全，不用再手动切线程。

**效果**：连续输入 `/user/get` 七个字符，从触发 7 次全量过滤 → 变成停下后触发 1 次。

> 120ms 是经验值：再小防抖不明显，再大会让人觉得“输入没反应”。

### 技术点 2：预计算 / 空间换时间（Memoization）

**概念**：把“每次都要重复算的结果”提前算好存起来，之后直接查。

观察到一个关键事实：**列表里的数据在一次会话中基本不变**，但旧代码每次按键都对每条 endpoint 重新归一化路径、重新编译正则。这些是纯浪费。

**做法**：列表加载时，为每一条预先算好一个“匹配键”并缓存起来。

```kotlin
// UrlPatternUtils.kt —— 端点的预计算匹配键
class EndpointKey internal constructor(
    val normalized: String,      // 归一化后的路径
    val normalizedLower: String, // 小写，供快速比较
    val regex: Regex             // 预先编译好的正则（复用，不重编）
)

fun buildEndpointKey(endpointPath: String): EndpointKey { ... }
```

对话框在数据到手时**一次性**算好所有键，并**预先按 url 排序**：

```kotlin
searchRows = list.map { SearchRow(it, UrlPatternUtils.buildEndpointKey(it.url)) }
    .sortedBy { it.item.url }   // 只在这里排一次
```

过滤时，查询串也只编译一次成“匹配器”，然后对每条做**纯字符串比较**（不再归一化、不再编译正则）：

```kotlin
val matcher = UrlPatternUtils.compileQuery(query)   // 每轮查询算一次
val matched = base.filter { matcher.matches(it.key) } // 热路径只做廉价比较
```

**顺带收益**：因为 `searchRows` 已经预先按 url 排好序，而 `filter` 是**保序**的（保持原有顺序），所以过滤后的结果天然有序，**省掉了每次按键的 `sortedBy` 全排序**。

> ⚠️ 小坑：正则编译 `toRegex` 遇到非法的 `{var:坏模式}` 会抛异常。旧代码是“用到时才编译”，一条坏数据只影响那一格；新代码改成“加载时批量预编译”，一条坏数据会中断整个列表构建。因此 `buildEndpointKey` 里加了 `try/catch`，编译失败就退化成“永不匹配的正则”（`Regex("(?!)")`），保留字符串比较能力，保证列表不会因一条脏数据而整个打不开。

### 技术点 3：结果数量上限（Limit）+ 减少重绘

**概念**：一次性渲染上千行 Swing 列表是非常贵的，尤其我们还用了 `<html>...</html>` 富文本渲染器（HTML 排版在 Swing 里出了名的慢）。

**现实考量**：命中上千条时，用户其实根本看不过来，继续细化查询才有意义。所以**显示层只画前 N 条**（默认 20，可在设置里选 10/20/50/100/200）。

```kotlin
// 只取前 limit 条去渲染，命中总数仍如实告诉用户
return Pair(matched.asSequence().map { it.item }.take(limit).toList(), matched.size)
```

状态行会提示“命中: 350，显示前 20（请细化查询）”，信息不丢失。

**为什么用 `asSequence().take(limit)`？**
`Sequence`（序列）是 **惰性求值** 的：`.map{}.take(limit)` 只会真正处理前 `limit` 个元素就停止，而不是先把整个列表 `map` 成新列表再截取。数据量大时能省掉大量无谓的对象创建。

> 类比：`List` 的 `.map{}.take(20)` = 先把一整仓库的苹果都洗一遍，再拿 20 个；
> `Sequence` 的 `.map{}.take(20)` = 边洗边拿，够 20 个就停手。

## 三、优化前后对比

| 环节 | 优化前 | 优化后 |
|------|--------|--------|
| 触发频率 | 每个字符触发一次全量过滤 | 停手 120ms 后触发一次（防抖） |
| 归一化路径 | 每条 endpoint 每轮都重算 | 加载时算一次并缓存 |
| 正则编译 | 每条 endpoint 每轮都重编 | 加载时预编译，复用 |
| 排序 | 每轮过滤后整体 `sortedBy` | 加载时预排一次，filter 保序免排 |
| 渲染行数 | 命中多少画多少（可能上千） | 最多画前 N 条（默认 20，可配） |
| 脏数据容错 | 用到时才编译，坏一条卡一格 | 预编译失败退化为纯字符串比较，不中断整表 |

## 四、涉及的关键知识点小结（便于延展搜索学习）

1. **EDT / 事件分发线程**：Swing 单线程模型，耗时操作会让界面卡顿。
2. **防抖 Debounce vs 节流 Throttle**：两者都是“降低高频回调频率”的手法，防抖是“等停下再做”，节流是“固定间隔最多做一次”。
3. **`javax.swing.Timer`**：回调运行在 EDT，适合“延时后更新界面”的场景。
4. **Memoization / 预计算 / 空间换时间**：把重复计算的结果缓存起来。
5. **正则表达式编译成本**：`Pattern`/`Regex` 编译开销大，应复用编译结果，别在循环里反复编译。
6. **保序过滤（filter preserves order）**：若源数据已排序，过滤后仍有序，可省去重复排序。
7. **惰性求值 `Sequence`**：`map/filter/take` 链式惰性计算，处理大集合更省内存和算力。
8. **列表重绘成本 & HTML 渲染器**：Swing 中 `<html>` 标签排版昂贵，减少可见行数是最直接的缓解手段。
9. **模态对话框后台加载 + `finishOnUiThread(ModalityState.any())`**：数据在后台线程算，回到 EDT 更新 UI；`ModalityState.any()` 保证回调在模态窗口打开期间不被挂起（详见代码注释）。

## 六、还可以继续做的事（进阶）

- 把列表渲染器从 `<html>...` 换成 **`AttributedCharacterIterator`（属性字符串）** 绘制灰色后缀，进一步消除偶发抖动（在已限行的情况下收益较小）。
- 若命中数经常巨大，可考虑**后台线程过滤 + 只把前 N 条回抛 EDT**，把 CPU 密集的比较也从 EDT 挪走。
- 更智能的排序：把“前缀匹配 / 精确匹配”排在“包含匹配”前面，让最相关的结果更容易出现在前 N 条里。
